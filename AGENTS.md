# Agent Guidelines — OMORI Wordle

This file provides essential information for agentic coding assistants working in this repository.

## Project Overview

OMORI Wordle is a daily word-guessing game themed around the RPG game *Omori*. Every day all players guess the same word — exclusively from the Omori universe (characters, locations, items, emotions, lore terms). Full-stack web application with optional authentication, database, statistics, and a friends-only daily leaderboard.

**Auth is optional** — the game is fully playable without an account. Signing in unlocks persistence, streak tracking, statistics, and the leaderboard.

**Package Manager**: pnpm  
**Deploy**: Vercel  
**Auth provider**: BetterAuth — Discord OAuth only

## Database Schema

Single source of truth: `db/schema.ts`. Always import inferred types from there — never duplicate type definitions manually.

Exported types: `User`, `GameResult`, `UserStats`, `Friendship`, `NewGameResult`, `NewFriendship`

### Key invariants

**`game_result`**
- `date` is `'YYYY-MM-DD'` string — never a timestamp
- `wordLength` stored explicitly — needed to reconstruct the grid in history without lookups
- `attempts`: `0` = loss, `1`–`6` = win
- `guesses`: `string[]` — full ordered sequence
- `timeSeconds`: nullable — player may leave the tab open overnight

**`user_stats`**
- 1:1 with `user` — `userId` is both PK and FK
- `lastPlayedDate`: if not yesterday → reset `currentStreak` to `1`
- `guessDistribution` keys: `'1'`–`'6'` for wins, `'0'` for losses
- Updated atomically inside `submitGame()` in the same transaction as `game_result`

**`friendship`**
- Bidirectional via duplicate rows: accepted friendship always has exactly two rows
- `(alice → bob, accepted)` + `(bob → alice, accepted)`
- Pending request = one row only
- Query "my friends": `WHERE requesterId = userId AND status = 'accepted'`
- Deleting or rejecting must delete both rows in a single transaction

## Word List

- Words range from **4 to 7 letters** — word length is dynamic per day
- Daily word selected deterministically by days since epoch (`2025-01-01`) — no API call needed
- Only words matching the day's word length are accepted as valid guesses
- Word curation is the owner's responsibility — never suggest adding or removing words without explicit instruction

## Code Style

- **TypeScript strict mode** — no `any`, no `// @ts-ignore`
- **Path aliases** — `@/components/...`, `@/lib/...`, `@/db/...`
- **Word casing** — always uppercase in storage and comparison, normalize user input before any check
- **Dates** — always `'YYYY-MM-DD'` strings, never `Date` objects in DB or day comparisons
- **Drizzle queries** — prefer `db.select().from(...).where(...)` over `db.query.*`; use `db.transaction()` for all multi-table writes
- **Components** — Server Components by default; add `'use client'` only when browser APIs or React state are genuinely needed
- **Tailwind** — utility classes only; no custom CSS files except global resets in `app/globals.css`

### Server Functions

All game logic lives in `actions/` as Server Functions (`'use server'`), not API routes. Always verify session at the top:

```ts
const session = await auth()
if (!session) throw new Error('Unauthorized')
```

API routes are used only for the BetterAuth handler and future webhooks or external consumers.

### State Management

- **In-progress game** → `localStorage` only (max 24h), helpers in `lib/gameState.ts`
- **Completed game (authenticated)** → database via `submitGame()`, server validates guess sequence before saving
- **Completed game (guest)** → `localStorage` only; result is never written to the DB
- **Stats and streak** → `user_stats`, updated in same transaction as `game_result`; not available for guests

### Guest Mode

Unauthenticated players can play the full game without restriction. After completing a game they see a prompt to sign in and save their result. If they sign in on the same day, the result from `localStorage` can be submitted retroactively via `submitGame()`.

Never gate the core game loop behind authentication. Auth UI (sign-in prompt, stats, leaderboard, friends) is shown as an opt-in overlay or separate page — never as a blocker.

## Ground Rules for Agents

- **Propose, don't apply.** Always show a diff or code block and wait for explicit approval before changing schema, auth config, or word lists.
- **Ask before creating new files.** State the intended path and reason first.
- **Do not install packages without asking.** List what and why — the owner decides.
- **Never touch BetterAuth internals.** Only `username` and `bio` on the `user` table are custom. Everything else is owned by the library.
- **Never write raw SQL.** No `db.execute()` with raw strings.
- **Never gate the game behind auth.** Any check that prevents an unauthenticated user from playing is wrong. Auth features (stats, leaderboard, friends) are opt-in only.

## What NOT to Do

- Do not create a `wordList` database table — words live in `data/`, not the DB
- Do not add email/password auth — Discord OAuth is the only provider
- Do not expose the daily word to the client before game completion — not in bundles, API responses, or cookies
- Do not create a global leaderboard — leaderboard is friends-only
- Do not add `console.log` to production code paths
- Do not edit files in `db/migrations/` — generated by `drizzle-kit generate`
